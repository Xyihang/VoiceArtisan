# 规格：可视化启动器 —— 过程可视化 + 性能优化（SPEC-LAUNCHER-UX-1）

> 状态：**待评审**（评审通过后再实施；本轮**不打包**）
> 对象：`launcher/qwentts_launcher.py`（tkinter 单文件启动器，1975 行）+ 打包后的 `launcher/dist/QWENTTS-Setup.exe`
> 起因：用户反馈「过程中等待烦躁」，希望启动器把过程讲清楚、等待不焦虑，并做性能优化

---

## 1. 需求澄清清单

### 核心诉求
启动器执行长任务（装依赖 5–20 分钟、构建前端 1–3 分钟、启动服务 10–60 秒）时，**用户不知道进度到哪、还要多久、能不能关**，于是烦躁。

### 目标用户
- 第一次装的普通用户（不知道 pip / venv 是什么）
- 换机器/重装的老用户（只想知道「还要等多久」）
- 你（排障时想快速看到体检结论）

### 使用场景
1. 双击 `start.bat` → 启动器出现 → 用户盯着界面等 10 分钟装依赖
2. 装依赖到一半去了趟洗手间，回来想确认「有没有卡住」
3. 启动服务后不知道成功没有，反复点「打开界面」
4. 体检扫模型目录（13GB）时界面像卡住

### 功能范围

**Must Have（P0）**
1. **步骤条**：`选目录 → 体检 → 装依赖 → 构建前端 → 生成配置 → 启动服务 → 完成`，7 步各自状态（等待/进行中/完成/跳过/失败）
2. **统一进度区**：进度条 + 百分比 + 当前动作文案 + 已用时 + 预计剩余
3. **pip 进度解析**：把 pip 输出解析成「第 N/M 个包」，不再只有滚动的原始日志
4. **窗口标题同步进度**：最小化后在任务栏也能看到「装依赖 42%」
5. **启动服务阶段可视化**：健康检查轮询显示「已探测 3/30 秒」，成功即弹「服务已就绪」并高亮「打开界面」
6. **界面先出、体检分两段**：先出窗口 + 快检（<0.5s），慢检（依赖/GPU/模型）后台补齐
7. **模型体积缓存**：13GB 目录不再每次全量遍历

**Should Have（P1）**
8. 失败时给「一键修复」按钮（把 fix_hint 里的命令直接执行/复制）
9. 日志面板限行（保留最近 2000 行）+ 仅在滚动到底部时自动滚动
10. 关闭窗口时若任务在跑 → 二次确认「仍在安装，退出会中断，确定吗？」
11. 依赖探测缓存（同解释器 10 分钟内不重复 import torch）
12. 前端构建智能跳过：`frontend/dist` 比 `frontend/src` 新则跳过并标注「已是最新，跳过」

**Nice to Have（P2）**
13. 阶段里程碑提示音/系统通知（Windows 通知）
14. 「导出本次安装报告」按钮（把日志 + 体检结果存成 txt）
15. 深色主题跟随系统

**Won't Have（明确不做）**
- 不改后端与前端 Web 界面
- 不引入新依赖（保持单文件 tkinter，不装 PyQt/CustomTkinter）
- 不做多语言
- 不做自动下载模型（仍在 Web 界面里做）

### 技术约束
- 单文件、仅标准库 + tkinter；打包用现有 PyInstaller 流程
- 所有阻塞操作必须在 worker 线程；UI 只通过 `queue` + `after(120ms)` 消息泵更新
- 兼容 Windows 10/11、125%/150% 高 DPI、中文路径

### 待确认问题（评审时定）
- [ ] 步骤条是否允许「跳步」（例如用户只点「启动服务」，前面步骤显示为「未执行」灰色）→ 建议允许，状态用「跳过」
- [ ] 进度条遇到无法解析的时长（如 pip 解析包数）时，是否接受「不确定进度（indeterminate）+ 已用时」→ 建议接受
- [ ] 是否需要把启动器做成「可最小化到托盘」→ 建议不做（P2 之外）

## 2. 现状与问题（基于代码实测）

| 位置 | 现状 | 问题 |
| --- | --- | --- |
| `_build_ui` | 顶部标题 + 目录 + 环境 + 体检 Treeview + 按钮 + 日志 + 状态栏 | **没有任何进度条/步骤指示**，只有一行「当前步骤：xxx」文字 |
| `_auto_checks_once` → `collect_checks` | 启动即同步跑完 10 项体检（`probe_python_deps` 会 `import torch`，`detect_model` 会 `dir_size` 遍历 13GB） | 界面出来但表格空白 10–60 秒；用户以为卡死 |
| `dir_size` | 每次都全量遍历模型目录 | 13GB 模型目录遍历数百毫秒到数秒，且每次体检都做 |
| `probe_python_deps` | 每次体检都起子进程 `import torch`（timeout 180s） | 冷启动 3–15 秒；重复体检重复付代价 |
| `stream_command` / `_run_stream` | 逐行把原始输出塞进日志 | 装依赖时是滚动日志海洋，用户看不出「到哪了」 |
| `task_install_deps` | 两段 pip（torch 源 + 镜像源），失败自动换源重试 | 全程无百分比；重试时用户不知道在重试 |
| `task_start_service` + `_health_ok` | 起服务后轮询健康检查 | 只有日志行，没有「已等 N 秒 / 上限 M 秒」的可视反馈 |
| `_drain_queue` | 每 120ms 批处理队列 | 合理，但 `_log_now` 单条 insert，日志无上限，长任务后 Text 控件越来越大 → 滚动卡 |

## 3. 功能规格

### 3.1 步骤条（P0）

- **输入**：任务开始/结束事件、`_start_task(label)` 的 label
- **处理**：维护 7 步状态机；`_start_task` 时把对应步骤置 `running`，`_finish_task` 置 `ok/failed`；未点过的按钮对应步骤保持 `idle`，点「启动服务」时前面未做的步骤标 `skipped`
- **输出**：横向步骤条（`tk.Canvas` 或 `ttk.Progressbar` 风格自绘），每步显示：序号圆点 + 名称 + 状态色（灰/蓝闪/绿/红/浅灰）
- **异常处理**：任一步骤失败 → 该步标红，后续步骤保持灰，状态栏给出「第 3 步失败：装依赖（详见日志）」

### 3.2 统一进度区（P0）

布局（自上而下）：

```
[步骤条：① 选目录  ② 体检  ③ 装依赖  ④ 构建前端  ⑤ 生成配置  ⑥ 启动服务  ⑦ 完成]
[━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ 42% ━━━━━━━━━━━]  已用 03:12 ｜ 预计还需 04:30
当前动作：正在下载 torch-2.4.1+cu121（第 6/23 个包）
```

- **输入**：worker 线程通过新的 `progress` 消息 `(phase: str, done: int|None, total: int|None, text: str)` 上报
- **处理**：
  - `done/total` 都有 → determinate，`percent = done/total`
  - 只有 `text` → indeterminate（进度条来回跑），但仍显示已用时
  - 用最近 30 秒的速率估算 ETA（`elapsed / percent - elapsed`），无速率时不显示 ETA
- **输出**：`ttk.Progressbar` + 三行文字（百分比/已用+ETA/当前动作）
- **异常处理**：任务失败 → 进度条变红、文字显示「已停止（第 3 步失败）」

### 3.3 pip 进度解析（P0）

- **输入**：`stream_command` 的每一行
- **处理**（逐行正则）：
  - `Collecting <pkg>` → `done_packages += 1`，记录当前包名
  - `Downloading <file>` / `Using cached <file>` → 当前动作文案
  - `Installing collected packages:` → 阶段切到「安装」
  - `Requirement already satisfied` → 计入已满足计数
  - 解析到 `-r requirements.txt` 的条目数作为 `total`（启动前 `pip install --dry-run -r ... -q 2>&1 | grep Collecting`？—— 不做 dry-run，改用 **requirements 文件行数** 作为分母，标记为「约」）
- **输出**：`progress("安装依赖", done, total≈N, "正在下载 torch…")`
- **异常处理**：解析不到时退化为 indeterminate，不报错

### 3.4 窗口标题 + 任务栏进度（P0/P2）

- 标题：`声匠启动器 · 装依赖 42%`；空闲时 `声匠启动器 · 就绪`
- Windows 任务栏进度（P2，可选）：`ctypes` 调 `ITaskbarList3`；失败静默忽略

### 3.5 启动服务可视化（P0）

- 起服务后：进度文案「已启动进程，正在探测 https://localhost:8443（3/30 秒）」
- 每 1 秒探一次健康检查，成功 → 步骤 ⑥ 变绿，弹提示「服务已就绪」，「打开界面」按钮高亮（主色）+ 自动聚焦
- 30 秒未就绪 → 显示「还没就绪，可能仍在加载模型；点『打开日志目录』查看」，按钮保持可点

### 3.6 体检两段式（P0）

| 段 | 内容 | 目标耗时 |
| --- | --- | --- |
| 快检 | Python 版本、pip、venv、磁盘、配置、前端产物、模型**目录是否存在** | ≤ 300ms |
| 慢检 | 后端依赖（torch/qwen-tts）、GPU、模型**体积/完整性**、Node、ffmpeg | ≤ 10s（命中缓存 ≤ 1s） |

- 快检结果**立即**渲染进 Treeview，慢检项先显示「检测中…」行，结果回来逐行替换（不整表重刷）
- 状态栏显示「体检进行中 3/8」

### 3.7 缓存（P0/P1）

- **模型体积**：写 `launcher.json` → `{"model_sizes": {"<abs path>": {"size": int, "mtime": float}}}`
  - 命中条件：路径存在且 `mtime` 未变 → 直接用；未变仍后台复核一次（每 10 分钟）
- **依赖探测**：`launcher.json` → `{"deps_probe": {"<python_exe>": {"ts": float, "info": {...}}}}`，TTL 10 分钟，界面提供「重新检测」
- **前端构建判定**：`max(mtime of frontend/src/**)` vs `frontend/dist/index.html` 的 mtime → dist 更新则跳过构建

### 3.8 日志与交互（P1）

- 日志保留最近 2000 行（超出从头部删），渲染批量（每 120ms 一次 insert）
- 仅当滚动条在底部时自动滚动，用户往上翻则不打扰
- 关闭窗口时若 `busy` → `messagebox.askyesno("仍在执行：装依赖，退出会中断，确定吗？")`
- 失败后按钮区出现「重试本步」+「复制修复命令」

## 4. 非功能需求

### 4.1 性能
| 指标 | 目标 | 现状 |
| --- | --- | --- |
| 窗口出现到可点击 | ≤ 1.0s | ≈ 0.6s（已有） |
| 首次体检出现第一行结果 | ≤ 0.5s | 10–60s |
| 体检全部完成（缓存未命中） | ≤ 12s | 同左但期间无反馈 |
| 体检全部完成（缓存命中） | ≤ 1.5s | 每次 10–60s |
| 装依赖期间 UI 卡顿 | 无（单帧 ≤ 50ms） | 日志大量 insert 时有轻微卡 |
| 日志控件内存 | ≤ 2000 行常驻 | 无上限 |

### 4.2 兼容性
- Windows 10/11 x64；tkinter DPI 缩放 100%/125%/150% 下布局不重叠
- 中文路径、含空格路径（`E:\My Projects\声匠`）

### 4.3 可靠性
- 消息泵任何异常不得让 `busy` 卡死（现有约束，继续保持）
- 缓存文件损坏 → 忽略并重建，不阻塞启动
- 网络不可用时 pip 失败重试逻辑保持现状

## 6. 接口规格（内部消息协议）

`self.q` 现有消息：`log / step / tip / checks / env / done`。新增：

| 消息 | 载荷 | 用途 |
| --- | --- | --- |
| `progress` | `{"phase": "装依赖", "done": 6, "total": 23, "text": "下载 torch…"}` | 驱动进度条与当前动作 |
| `stage` | `{"step": "deps", "state": "running|ok|failed|skipped"}` | 驱动步骤条 |
| `notify` | `{"level": "info|warn|error", "title": "...", "text": "..."}` | 里程碑提示（可选系统通知） |

## 7. 验收标准

- [ ] 冷启动：窗口出现 ≤ 1.0s，且**首行体检结果 ≤ 0.5s**
- [ ] 体检完成（缓存命中）≤ 1.5s；未命中 ≤ 12s，期间状态栏显示 `体检进行中 k/8`
- [ ] 点「安装依赖」后 3 秒内出现进度条与「第 N/M 个包」文案，且有百分比（解析失败时退化为 indeterminate）
- [ ] 装依赖全程 UI 可交互（按钮置灰但窗口可拖动、可切页、日志实时滚）
- [ ] 任务栏标题显示 `装依赖 xx%`；完成后恢复 `就绪`
- [ ] 点「启动服务」后显示 `探测中 k/30 秒`，成功时「打开界面」按钮高亮并弹就绪提示
- [ ] 关窗口时任务在跑 → 弹二次确认
- [ ] 日志超过 2000 行后内存不增长（Text 行数恒定）
- [ ] 缓存命中/失效两种情况都正确（改模型目录 mtime 后 10 分钟内应复核）
- [ ] 无新增第三方依赖；`python launcher/qwentts_launcher.py --selfcheck` 仍工作
- [ ] PyInstaller 重新打包后体积增长 ≤ 1 MB

## 8. 风险与依赖

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| pip 输出格式随版本变化 | 解析失败、进度条退化为 indeterminate | 正则宽松匹配 + 解析失败不影响任务；只做「锦上添花」 |
| requirements 行数 ≠ 实际包数（含依赖树） | 百分比不准 | 文案标明「约 N 个包」，且到 95% 封顶，最后 5% 留给收尾 |
| tkinter 高 DPI 下 Canvas 自绘步骤条错位 | 视觉瑕疵 | 用 `ttk.Frame` + `Label` 拼装（不用 Canvas），并做 125%/150% 实测 |
| 缓存写坏 launcher.json | 启动失败 | 读写全部 try/except，损坏则重建默认值 |
| 打包后 `ctypes` 任务栏进度在旧系统不可用 | 无进度 | 静默降级，不影响主流程 |

## 9. 实施顺序（评审通过后）

1. 消息协议 + 步骤条 + 进度条骨架（不改逻辑，先能显示）
2. 体检两段式 + 缓存（性能大头）
3. pip 解析 + 标题/任务栏进度
4. 启动服务探测可视化 + 就绪提示
5. 日志限行/滚动策略 + 退出确认 + 失败重试按钮
6. 125%/150% DPI 与打包验证（**本轮不打包**，仅本地 `python launcher/qwentts_launcher.py` 与 `QWENTTS-Setup.exe` 重建验证）
